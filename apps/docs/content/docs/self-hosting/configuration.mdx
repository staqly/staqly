Staqly Community Edition works without any configuration. Come here when you need to change
something: a port, the public URL for phones, media storage, OAuth apps, log level or retention. All settings are environment
variables; how you pass them depends on how you run staqly.

## How to change a setting

<Tabs items={["Binary", "Docker"]}>
<Tab value="Binary">

Set the variable in the environment of `staqly serve`. The binary does not read a `.env` file.

```bash
LOG_LEVEL=debug PUBLIC_DASHBOARD_URL=http://192.168.1.23:8080 staqly serve --expose
```

For a long-running install, put them in your service definition (for systemd:
`Environment=LOG_LEVEL=debug`). See [Run the binary](/self-hosting/binary).

`staqly serve` sets a few variables itself, from its flags:

| Variable | Set by `staqly serve` to |
|---|---|
| `DATA_DIR` | `--data`, else `$STAQLY_DATA_DIR`, else `~/.local/share/staqly` |
| `ADDR` | `127.0.0.1:<--port>` (default `3333`) |
| `DASHBOARD_ADDR` | `127.0.0.1:<--dashboard-port>`, or all interfaces with `--expose` |
| `PUBLIC_API_URL` | `http://localhost:<--port>`, unless you set `PUBLIC_API_URL` |
| `LOG_FORMAT` | `text`, unless you set `LOG_FORMAT` |

Setting `DATA_DIR`, `ADDR` or `DASHBOARD_ADDR` yourself has no effect — use the flags.

</Tab>
<Tab value="Docker">

Pass each variable to `docker run` with `-e NAME=value`, or put them in a file and add
`--env-file staqly.env`:

```bash title="staqly.env"
LOG_LEVEL=debug
PUBLIC_DASHBOARD_URL=http://192.168.1.23:8080
```

A container keeps the settings it was created with. To change one, remove the container and run
it again with the new value; the data stays in the volume:

```bash
docker rm -f staqly
docker run -d --name staqly ... --env-file staqly.env ghcr.io/staqly/staqly:latest   # your full command
```

See [Run with Docker](/self-hosting/docker#settings).

Developing from a checkout with [Docker Compose](/self-hosting/docker-compose)? Put the variables in
`.env` in the repository root and run `docker compose up -d`. `compose.yml` passes most of them
through; the ones marked "not passed through by `compose.yml`" below need a line in the
`staqly` service's `environment:` first.

</Tab>
</Tabs>

Invalid values refuse to start instead of falling back silently: staqly exits with a
`config: <reason>` error (see [Troubleshooting](/self-hosting/troubleshooting)).

## Mode and access

| Variable | Default | Description |
|---|---|---|
| `STAQLY_MODE` | `local` | `local`: Staqly Community Edition, one workspace, no limits, every request with the access token, API for this machine only. Leave it unset: the other mode, `cloud`, runs the hosted [Staqly Cloud](/local-vs-cloud) and is not a supported self-hosting setup. Trimmed and case-insensitive; any other value refuses to start. |
| `STAQLY_LOCAL_TOKEN` | — | Community Edition (local mode): fixes the [access token](/local-vs-cloud#the-access-token) (`stk_local_` and at least 32 characters in all) instead of the file `DATA_DIR/access_token`, which is made on first start (mode 0600). For tests and CI; `server token --rotate` then refuses. An invalid value refuses to start. |
| `LOCAL_TRUSTED_PEERS`, `LOCAL_ALLOWED_HOSTS`, `LOCAL_ALLOWED_ORIGINS` | — | No longer read: they guarded the keyless local mode of earlier versions. The Community Edition now needs the access token for every request; staqly warns at start when one of them is still set. |
| `COOKIE_SECURE` | `false` | Mark session cookies `Secure`. Set `true` when browsers reach the dashboard only over HTTPS (your own reverse proxy). |
| `TRUST_PROXY` | `false` | Take the client IP from the right-most `X-Forwarded-For` entry (rate limits, logs). Only behind your own reverse proxy. |
| `LOCAL_USER_NAME` | your login name with the binary (compose passes `$USER`), else `Local` (the Docker image without `-e LOCAL_USER_NAME="$USER"`) | Community Edition: the name shown for you in the activity log. |
| `SESSION_TTL` | `720h` | Browser session lifetime (Go duration). |
| `DASHBOARD_ADDR` | — | Also serve the dashboard from the API process on this address. `staqly serve` sets it; the Docker image sets `:8080`. |
| `DASHBOARD_EXPOSED` | `true` if `DASHBOARD_ADDR` is not loopback, else `false`; `true` in the Docker image | The dashboard is open to the network: *Connect a device* links opened as `localhost` point at this computer's Wi-Fi address instead. With the binary this follows `--expose`. |

## URLs and ports

| Variable | Default | Description |
|---|---|---|
| `API_PORT` | `3333` | Compose only: host port for the API (bound to `127.0.0.1`). With `docker run` change the `-p` mapping and `PUBLIC_API_URL`; with the binary use `--port`. |
| `DASHBOARD_PORT` | `8080` | Dashboard port. Docker: the published host port (set it when you map the dashboard to another host port). Binary: follows `--dashboard-port`. Also part of sign-in links, such as the `#token=` link printed at start. |
| `PUBLIC_API_URL` | `http://localhost:3333` | Base of absolute media URLs in API responses and webhook payloads. Set it to what receivers can reach (e.g. `http://api:3333` for n8n on the Docker network, or your public URL). The dashboard reads it from the API at runtime, so changing it needs only a restart. With the binary it defaults to `http://localhost:<--port>`. |
| `PUBLIC_DASHBOARD_URL` | — | Dashboard URL used in *Connect a device* QR codes, sign-in links and notification links — your LAN IP (`http://192.168.1.23:8080`) or domain. Without it, QR codes use the address you opened the dashboard at; an exposed `staqly serve` opened as `localhost` uses this computer's Wi-Fi address instead, and in Docker the dialog asks for that address once (kept in the browser). `connect-link` and notification links fall back to `localhost`. |
| `ADDR` | `127.0.0.1:3333` | Listen address of the API. The Docker image sets `ADDR=:3333` (publish the port on `127.0.0.1` only); `staqly serve` sets `127.0.0.1:<--port>`. |

## Storage and limits

| Variable | Default | Description |
|---|---|---|
| `DATA_DIR` | `./data`; `/data` in Docker; `~/.local/share/staqly` with the binary | Data directory. With the binary use `--data` or `STAQLY_DATA_DIR`. |
| `DATABASE_PATH` | `$DATA_DIR/workspace.db` | The SQLite database file. |
| `UPLOAD_DIR` | `$DATA_DIR/uploads` | Media files, with `STORAGE_DRIVER=disk`. |
| `STORAGE_DRIVER` | `disk` | Where media files live: `disk` (`UPLOAD_DIR`) or `s3`, any S3-compatible bucket (AWS S3, Cloudflare R2, MaxIOFS...). See [Media storage](/self-hosting/storage). |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | none | Required with `STORAGE_DRIVER=s3`; the server refuses to start without them. |
| `S3_REGION` | `us-east-1` | The bucket's region. |
| `S3_FORCE_PATH_STYLE` | `false` | `true` puts the bucket in the URL path, as MaxIOFS, MinIO and most self-hosted servers need. |
| `S3_PREFIX` | none | A folder in the bucket for staqly's files, e.g. `staqly/`. |
| `S3_PUBLIC_URL` | none | Public URL of the bucket (usually a CDN). Platforms that fetch media get links there instead of signed links. |
| `S3_SIGN_ENDPOINT` | `S3_ENDPOINT` | The address platforms reach the bucket at, when staqly reaches it at another one (staqly on an internal network, platforms through a proxy or tunnel). Signed links point here. |
| `S3_CREATE_BUCKET` | `false` | Create a missing bucket on start. Otherwise a missing bucket stops the server with a clear message. |
| `MAX_UPLOAD_MB` | `100` | Maximum upload size. |
| `JOB_CONCURRENCY` | `4` | Background [jobs](/concepts#jobs) (publishing, schedule runs, sign-in refreshes) run at once, at most `64`; one workspace gets at most half while another waits. |
| `PROCESSING_TIMEOUT` | `1h` | Server default for how long a target on [your own automation](/channels/your-own-automation) may wait for a reported result before it fails with *No result reported in time* (`post.target_failed`). A Go duration such as `30m` or `6h`; `0` turns it off. A collection can set its own value (**Fail publishing if nothing is reported within** in its settings, `processing_timeout_seconds` on `PATCH /v1/collections/{id}`, 1 minute to 24 hours), which wins over this default. |

## Channels and secrets

| Variable | Default | Description |
|---|---|---|
| `STAQLY_SECRET_KEY` | — | Seals channel credentials and developer app secrets (AES-256-GCM): 32 bytes, base64-encoded (`openssl rand -base64 32`). If unset, a key is generated into `DATA_DIR/secret.key` (mode 0600) on first start. **Back it up with the database**: without it every channel has to be reconnected. An invalid value refuses to start. |
| `PROVIDER_<ID>_ENABLED` | `true` | `false` turns one platform off on this server: no tile, no connecting, no publishing (e.g. `PROVIDER_TIKTOK_ENABLED=false`). See [Developer apps](/channels/developer-apps). |
| `PROVIDER_<ID>_CLIENT_ID`, `PROVIDER_<ID>_CLIENT_SECRET` | — | The OAuth developer app of one platform, e.g. `PROVIDER_X_CLIENT_ID` / `PROVIDER_X_CLIENT_SECRET`. See [Developer apps](/channels/developer-apps). |

## Editors: AI and stock photos

### AI tools

The [design editor's AI tools](/dashboard/design-editor#ai-tools) and the media library's AI videos run on the
server's own provider accounts. Keys are read on the server only: no browser, workspace or API response ever sees
them. With both keys fal.ai is the primary and Higgsfield the fallback (for what it does the same way); with one,
that one runs alone; with none, the AI tools are hidden. A provider that is down is not the same as one that is not
set up: its requests fail (or fall back) and the tools stay. A key of the wrong shape refuses to start.

| Variable | Default | Description |
|---|---|---|
| `AI_FAL_KEY` | — | A [fal.ai](https://fal.ai/dashboard/keys) API key. Turns on every AI tool. |
| `AI_HIGGSFIELD_API_KEY` | — | A [Higgsfield](https://console.higgsfield.ai) API key as `<key id>:<key secret>`. Alone: new pictures and videos; with `AI_FAL_KEY`: their fallback. |
| `AI_ASSISTANT_MODEL` | `google/gemini-2.5-flash` | The language model of the dashboard's [assistant](/dashboard/assistant), an OpenRouter model id run through fal.ai's router (needs `AI_FAL_KEY`). Pick one that calls tools well. |
| `AI_OPERATIONS` | every one | The tools offered, comma-separated: `generate`, `edit`, `inpaint`, `erase`, `expand`, `remove_background`, `replace_background`, `upscale`, `enhance`, `text_to_video`, `image_to_video` (e.g. `generate,edit,erase` keeps videos off). |
| `AI_PRICES` | built in | Overrides the estimate of a model, `model=price` per its unit (image, megapixel or video second), comma-separated: `fal-ai/flux/schnell=0.004,fal-ai/flux-pro/kontext=0.05`. |
| `AI_FAL_BASE_URL` | `https://queue.fal.run` | fal.ai's queue API (a proxy or tests). |
| `AI_HIGGSFIELD_BASE_URL` | `https://api.higgsfield.ai` | Higgsfield's API (a proxy or tests). |

How a request runs: it is checked (scope `media:write`, the workspace, the picture: PNG, JPEG or WebP up to 20 MB
and 4096 px a side, the limits), its picture is kept as a temporary file and the job queue sends it to the
provider, then asks how it is going until the result is in. The worker sends a request once: a provider that did not
answer may have started it, so it is never sent again or to the fallback (Higgsfield deduplicates by the job id,
so only it gets the same request again after a lost answer). A failed request is not retried; the person asks
again. Every request is recorded with the person, the provider, the model, the operation, how long it took and
its estimated cost (the `ai_jobs` table); its files and the description are deleted once the result is used or
discarded, or after a day. Higgsfield is asked to delete its copy once the result is in; fal.ai keeps results on
its CDN under your account's retention setting (set it in fal.ai's dashboard). Logs name the job, the provider and
the model, never a key, a description or a picture.

To try the tools locally, put a key in `.env` (or the environment of `staqly serve`) and restart; the AI tool
appears in the editor. Every request is billed by the provider, so test with a few requests first.

### Stock photos

| Variable | Default | Description |
|---|---|---|
| `UNSPLASH_ACCESS_KEY` | — | An [Unsplash](https://unsplash.com/developers) app's access key: the [design editor](/dashboard/design-editor) gets an **Unsplash** tab with stock photos. The key stays on the server; searches go through staqly, the pictures load from Unsplash. Unset, the tab is not shown. |

## Webhooks and schedule endpoints

| Variable | Default | Description |
|---|---|---|
| `WEBHOOK_ALLOW_PRIVATE` | `true` | Allow webhook deliveries and [schedule endpoint](/automation/schedules#call-an-endpoint-source-endpoint) calls to private addresses (LAN, Docker networks, e.g. n8n). |
| `WEBHOOK_ALLOW_LOOPBACK` | `false` | Allow deliveries to `127.0.0.1` / `::1`. Useful with the binary when a receiver (e.g. n8n) runs on the same computer. |
| `WEBHOOK_RETRY_BASE` | `15s` | First retry delay; doubles per attempt. |
| `WEBHOOK_RETRY_MAX` | `1h` | Maximum retry delay. |
| `WEBHOOK_LEASE` | `2m` | How long a delivery being sent stays claimed; one in flight when the process died is sent again after it. Longer than `1m` (the longest attempt). |

## Alerts

| Variable | Default | Description |
|---|---|---|
| `NOTIFY_SECRET_KEY` | — | Encrypts alert secrets (bot tokens, SMTP passwords); **at least 32 bytes** (e.g. `openssl rand -hex 32`) — shorter values refuse to start. If unset, a key is generated into `DATA_DIR/notify_secret.key` — back it up with the database. |
| `NOTIFY_ALLOW_PRIVATE` | `false` | Allow alerts to post to LAN addresses (self-hosted ntfy, SMTP relay). |
| `NOTIFY_DISABLED_GRACE` | `24h` | How long a disabled alert keeps its queued messages before they are skipped. |
| `NOTIFY_ALLOW_LOOPBACK` | `false` | Allow alerts to post to this machine (127.0.0.1), e.g. a local ntfy. |
| `NOTIFY_MAX_ATTEMPTS` | `5` | Attempts per message before it is marked failed. |
| `NOTIFY_RETRY_BASE` | `30s` | First retry delay; doubles with every attempt. |
| `NOTIFY_MAX_FAILS` | `10` | Consecutive failures after which an alert is disabled automatically. |
| `NOTIFY_CONCURRENCY` | `8` | Alerts sent to in parallel. |
| `NOTIFY_POLL_INTERVAL` | `2s` | How often the alert worker checks for due messages. |
| `TELEGRAM_API_BASE` | `https://api.telegram.org` | Base URL of the Telegram Bot API. Change it only for a self-hosted Bot API server or tests. |
| `SLACK_API_BASE` | `https://slack.com/api` | Base URL of the Slack Web API. Change it only for tests. |
| `DISCORD_API_BASE` | `https://discord.com/api/v10` | Base URL of the Discord API. Change it only for tests. |

`compose.yml` passes the `NOTIFY_*` settings through except `NOTIFY_ALLOW_LOOPBACK` and
`NOTIFY_POLL_INTERVAL`; add those and the `TELEGRAM_*`, `SLACK_*` and `DISCORD_*` ones to the
`staqly` service's `environment:` first. More in [Alerts → Configuration](/automation/alerts#configuration).

## Observability

| Variable | Default | Description |
|---|---|---|
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` or `error`. Anything else refuses to start. |
| `LOG_FORMAT` | `json`; `text` with the binary | `json` (one object per line on stdout) or `text`. See [Logs & tracing](/self-hosting/logs-and-tracing). |
| `METRICS_TOKEN` | — | Bearer token for `/metrics` from outside this machine (e.g. Prometheus in Docker). |
| `SENTRY_DSN` | — | Send errors (5xx, panics, failing workers) to Sentry. Off when empty. See [Logs & tracing](/self-hosting/logs-and-tracing#sentry). |
| `SENTRY_ENVIRONMENT` | `production` | Sentry environment name. |
| `POSTHOG_KEY` | — | Send product analytics and error reports to your own PostHog project (its project token, `phc_...`). Off when empty: nothing is sent. See [Analytics](/self-hosting/analytics). |
| `POSTHOG_HOST` | `https://eu.i.posthog.com` | PostHog ingestion host (US cloud, self-hosted PostHog or a reverse proxy). |
| `POSTHOG_ENVIRONMENT` | `production` | Added to every event; `development` and `test` are meant to be filtered out of dashboards. |
| `RATE_LIMIT_DISABLED` | `false` | Turn off rate limits. |
| `RATE_LIMIT_PER_MINUTE` | `10` | Sensitive unauthenticated endpoints, per IP. `RATE_LIMIT_BURST` defaults to the same value. |

See [Monitoring](/self-hosting/monitoring).

## Retention

| Variable | Default | Description |
|---|---|---|
| `RETENTION_DELIVERIES_DAYS` | `30` | Delete finished webhook deliveries after N days (`0` = keep). |
| `RETENTION_EVENTS_DAYS` | `0` | Delete events older than N days (`0` = keep forever). |
| `RETENTION_NOTIFICATIONS_DAYS` | `30` | Delete finished alert outbox rows after N days (`0` = keep). |
| `RETENTION_AGENTS_DAYS` | `30` | Remove agents and API connections (Integrations) not seen for N days; they come back when they talk again (`0` = keep). |

See [Data export & privacy](/self-hosting/data-export#retention).

## Containers and images

With `docker run`, the image tag, memory and process limits are part of the command
(`ghcr.io/staqly/staqly:v0.2.0`, `--memory 640m`, `--pids-limit 256`); see
[Run with Docker](/self-hosting/docker#what-the-flags-do). These variables are read by the Compose
files of a checkout ([Develop with Docker Compose](/self-hosting/docker-compose)):

| Variable | Default | Description |
|---|---|---|
| `STAQLY_VERSION` | `latest` | Tag of the pre-built image `ghcr.io/staqly/staqly` that `make up` pulls: `latest` or a release such as `v0.2.0`. Pin one to stay on it. |
| `STAQLY_MEM_LIMIT` | `640m` | Memory limit of the staqly container (`API_MEM_LIMIT`, its older name, still works). |
| `STAQLY_PIDS_LIMIT` | `256` | Process limit of the staqly container (`API_PIDS_LIMIT`, its older name, still works). |
| `API_INTERNAL_URL` | `http://localhost:3333` | Development only: where `pnpm --filter @staqly/platform dev` proxies `/api/*`. The staqly image serves the dashboard from the same process and does not need it. |
| `MAILPIT_PORT` | `8025` | Development stack only (`make dev`): host port of the mailpit inbox. See [Docker Compose](/self-hosting/docker-compose#development-stack). |
| `MAXIOFS_PORT`, `MAXIOFS_CONSOLE_PORT` | `9000`, `9001` | Development stack only: host ports of the MaxIOFS S3 API and its web console. |

## Install script

Read by `scripts/install.sh` (the `curl -fsSL https://raw.githubusercontent.com/staqly/staqly/main/scripts/install.sh | sh` installer), not by staqly itself:

| Variable | Default | Description |
|---|---|---|
| `STAQLY_VERSION` | latest release | Release tag to install, e.g. `v0.2.0`. |
| `STAQLY_INSTALL_DIR` | `~/.local/bin` | Where to put the `staqly` binary. |
