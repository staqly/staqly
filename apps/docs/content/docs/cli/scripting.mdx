---
title: Scripting recipes
description: Use the staqly CLI in shell scripts and CI to gate a step on human approval and act on the decision.
---

These recipes put a human in the loop of a shell script or CI job: the script pauses, a person
approves or rejects in the dashboard (or on their phone), and the script continues based on the
answer. Use them when your automation is already a shell script or a CI pipeline. If it is a
TypeScript or Python program, the [SDKs](/sdk/typescript) do the same with `requestApproval` /
`request_approval`.

## Your first approval gate

<Steps>
<Step>
### Install the CLI and point it at your server

Follow [Get started](/cli#get-started). In CI, set `STAQLY_API_URL` and `STAQLY_API_KEY` instead
of running `staqly login`.

</Step>
<Step>
### Push and branch on the exit code

`staqly push` waits for the decision and reports it through its [exit code](/cli#exit-codes):

```bash
staqly push Deploys --title "Release v1.4" --timeout 1h
case $? in
  0) ./deploy.sh ;;
  2) echo "Rejected, not deploying"; exit 1 ;;
  3) echo "Nobody decided in time"; exit 1 ;;
  *) echo "staqly error"; exit 1 ;;
esac
```

</Step>
<Step>
### Approve it

Open the dashboard, run `staqly inbox`, or tap the button in a
[notification](/automation/notifications). The script continues right away.

</Step>
</Steps>

## Require approval before deploying in CI

In GitHub Actions, `push` exits non-zero on anything but approval, so the next step only runs
when a human said yes:

```yaml
- name: Wait for human approval
  env:
    STAQLY_API_URL: https://staqly.example.com
    STAQLY_API_KEY: ${{ secrets.STAQLY_API_KEY }}   # scopes: items:write items:read
  run: staqly push Deploys --title "Deploy ${GITHUB_REF_NAME}" --external-ref "$GITHUB_SHA" --timeout 2h
- name: Deploy
  run: ./deploy.sh
```

Full walkthrough: [Agent approval gate in CI](/cookbook/ci-approval-gate).

## Report what happened after approval

Close the loop so reviewers can see whether the approved action actually worked:

```bash
out=$(staqly push Social --title "Post" --content "$text" --json); code=$?
[ "$code" -eq 0 ] || exit "$code"          # rejected, timed out or error: stop here
id=$(jq -r .id <<<"$out")

if url=$(./publish.sh "$text"); then
  staqly items result "$id" --status completed --result "{\"url\":\"$url\"}"
else
  staqly items result "$id" --status failed --error "publish failed"
fi
```

## Use the reviewer's feedback

A rejection usually says what to change. Read it from the JSON and feed it back into your
generator (`regenerate` stands for your own script):

```bash
result=$(staqly push Copy --title "Tagline" --content "$draft" --json); code=$?
feedback=$(jq -r .feedback <<<"$result")
[ "$code" -eq 2 ] && regenerate --hint "$feedback"
```

## Approve everything matching a search

```bash
staqly items list --status pending --q "typo fix" --all --json \
  | jq -r '.data[].id' | xargs staqly items approve --feedback "bulk"
```

## React to decisions in a shell loop

`events tail --follow --json` prints one event per line, so a `while read` loop can act on each
approval as it happens:

```bash
staqly events tail -f --type item.approved --json | while read -r ev; do
  id=$(jq -r .item_id <<<"$ev")
  publish "$id" && staqly items result "$id" --status completed
done
```

For a long-running service, a [webhook](/automation/webhooks) is more robust than a shell loop.
