title: Notifications
description: Get told when something needs review — and approve or reject right from Telegram, Slack, Discord, ntfy or email.
---

A workspace can have several **notification channels**. Each one sends a message when an
item needs review (or on any events you choose), and most let you **decide from the
message** without opening the dashboard.

| Type | Delivery | Decide from the message |
|---|---|---|
| `telegram` | Bot API message (images uploaded as photos) | Inline **Approve / Reject / Reject with reason** buttons |
| `slack` | Incoming webhook or `chat.postMessage` (Block Kit) | Buttons with a Slack app (signing secret); one-tap links otherwise |
| `discord` | Channel webhook (images attached) or a bot message | Buttons and a reason form with a Discord application; one-tap links otherwise |
| `ntfy` | ntfy publish (ntfy.sh or self-hosted) | **Approve / Reject** notification actions |
| `email` | SMTP (STARTTLS by default), HTML + text | Approve / Reject links |

Decisions made from chat or a link go through **the same path as the dashboard**: version
checks, `item.approved` / `item.rejected` events and your webhooks all fire as usual. The
actor is recorded as `Telegram: @name`, `Slack: name`, `Discord: name` or `Link: <channel name>`.

## Managing channels

Use the API (scope **`channels:manage`**, or `admin`) — dashboard sessions and local mode have
it implicitly:

```bash
curl -s -X POST http://localhost:3333/v1/notification-channels \
  -H 'Content-Type: application/json' -d '{
  "name": "My phone",
  "type": "ntfy",
  "config": { "topic": "staqly-7f3k9q2", "server_url": "https://ntfy.sh" },
  "events": ["item.created", "item.escalated"],
  "collection_ids": [],
  "digest_window_seconds": 0
}'
```

| Field | |
|---|---|
| `events` | Glob patterns. Default: a new item waiting for review (`item.created` — only notified when the new item is `pending`) and rule escalations (`item.escalated`). Add others such as `item.approved`, `item.rejected` or `item.*`. |
| `collection_ids` | Only these collections; empty = all. |
| `digest_window_seconds` | Collect everything within the window into one message (e.g. `300` = at most one message per 5 minutes). Digests keep per-item buttons for the first 10 items (5 on Discord). |
| `config` | Type-specific settings, below. |
| `enabled` | `false` pauses the channel. |

<Method m="GET" path="/v1/notification-channels" /> ·
<Method m="POST" path="/v1/notification-channels" /> ·
<Method m="PATCH" path="/v1/notification-channels/{id}" /> ·
<Method m="DELETE" path="/v1/notification-channels/{id}" />

- **Test**: `POST /v1/notification-channels/{id}/test` sends a test message now and returns
  `{"ok": true}` or `{"ok": false, "error": "…"}`.
- **History**: `GET /v1/notification-channels/{id}/deliveries` lists recent notifications
  with status `pending`, `sent`, `failed` or `skipped`.
- **Secrets** (`bot_token`, `webhook_url`, `signing_secret`, `access_token`, `password`) are
  encrypted at rest and always come back **masked** (`••••`). To keep a secret on update,
  send the masked value back or omit the key; send `null` to remove it.
- **Retries and failures**: sending is retried with backoff. After `NOTIFY_MAX_FAILS`
  consecutive failures (default 10) the channel is **disabled** (`enabled=false`,
  `disabled_reason` says why). Fix the cause and `PATCH {"enabled": true}` — messages queued
  meanwhile are delivered.
- **Stale items are skipped**: if an item is no longer pending when its notification is sent
  (e.g. a rule auto-approved it), the notification is `skipped`.
- **Plan limits** (cloud): Free 2 channels, Indie 10, Team unlimited — over the limit,
  `402 plan_limit_exceeded` with `details.limit = "notification_channels"`.

## One-tap decision links

ntfy, email, Slack without an app and Discord webhooks get **Approve / Reject links** like
`https://<api>/v1/decide/dl_…`:

- Each link is **single-use**, expires after 7 days (`NOTIFY_LINK_TTL`), and only a SHA-256
  hash of its token is stored.
- Opening a link (**GET**) shows a **confirmation page** with the item; only **POST** — the
  button on that page — decides. Link-preview bots and mail scanners can't approve anything by
  fetching the URL. ntfy's action buttons POST directly.
- The reject page has an optional **reason** field.
- An item someone already decided shows a friendly "already approved" message (`409`); a used
  or expired link returns `410`.
- Links are **bearer credentials** — anyone with the message can use them. Send them only to
  private destinations.

Links point to **`NOTIFY_PUBLIC_API_URL`** (default `PUBLIC_API_URL`), which must be reachable
from the device where you tap:

| Setup | `NOTIFY_PUBLIC_API_URL` |
|---|---|
| Laptop, tapping on the same laptop | default (`http://localhost:3333`) |
| Laptop, tapping on your phone (same Wi-Fi) | `http://<LAN IP>:8080/api` — through the dashboard, which proxies `/api/*` to the API |
| Cloud | your public HTTPS API URL |

"Open in dashboard" links use `PUBLIC_WEB_URL` (`…/items/{id}`).

## Telegram

<Steps>
<Step>
In Telegram, open **@BotFather**, send `/newbot`, choose a name and copy the **bot token**
(`123456:ABC…`).
</Step>
<Step>
Open a chat with your new bot and send `/start`.
</Step>
<Step>
Find your **chat ID**: open `https://api.telegram.org/bot<TOKEN>/getUpdates` in a browser and
read `message.chat.id` — or create the channel with any chat ID and send `/chatid` to the bot,
which replies with the chat ID and your user ID. For a group, add the bot to the group and use
the group's (negative) ID.
</Step>
<Step>

Create the channel:

```json
{ "name": "Telegram", "type": "telegram", "config": { "bot_token": "123456:ABC…", "chat_id": "123456789" } }
```

</Step>
</Steps>

- **Buttons**: ✅ **Approve** / ❌ **Reject** decide immediately and are replaced by the result
  ("✅ Approved by @you"). 💬 **Reject with reason** asks you to *reply* with the reason; your
  reply rejects the item and becomes its feedback.
- **Who may decide**: by default only the user whose private chat is `chat_id`. For groups set
  `approver_user_ids` (numeric Telegram user IDs); everyone else gets "You are not on this
  channel's approver list".
- **`mode: "polling"`** (default): staq.ly long-polls Telegram (`getUpdates`, every
  `TELEGRAM_POLL_INTERVAL`). **Works on a laptop with no public URL.** Use one channel per bot —
  two pollers on one bot steal each other's updates.
- **`mode: "webhook"`** (cloud): when the channel is saved, staq.ly calls `setWebhook` with
  `NOTIFY_PUBLIC_API_URL/v1/integrations/telegram/{channel_id}` and a random secret token, so
  Telegram must reach your API over HTTPS. Switching back to polling calls `deleteWebhook`.

Walkthrough: [Approve from chat](/docs/cookbook/approve-from-chat).

## Slack

**Simplest — messages with link buttons:** create an app at api.slack.com/apps, enable
**Incoming Webhooks**, *Add New Webhook to Workspace*, pick a channel and copy the URL:

```json
{ "name": "Slack", "type": "slack", "config": { "webhook_url": "https://hooks.slack.com/services/…" } }
```

**Interactive buttons (decide inside Slack):** in the same app enable **Interactivity &
Shortcuts** with the Request URL `https://<your-api>/v1/integrations/slack/interactions` (the
channel's `integration_url` shows it), copy the **Signing Secret**, and set `signing_secret`
and `approver_user_ids` (Slack member IDs, `U…`). Requests are verified with
`X-Slack-Signature` and must be at most 5 minutes old; presses from anyone not on the list are
refused — an empty list means nobody can decide from Slack. *Reject with reason…* opens the
confirmation page.

Instead of a webhook you can use `bot_token` (`xoxb-…`, scope `chat:write`) plus `channel` (a
channel ID). Interactive buttons need a public HTTPS URL; Socket Mode isn't supported.

## Discord

**Simplest — a channel webhook** (*Server Settings → Integrations → Webhooks → New Webhook*):

```json
{ "name": "Discord", "type": "discord", "config": { "webhook_url": "https://discord.com/api/webhooks/…" } }
```

Messages are embeds with **Approve… / Reject…** links; images are attached; `@everyone` and
other mentions are neutralised.

**Buttons (decide inside Discord):** create an application, add a bot (copy its **token**,
invite it with *Send Messages*), copy the **Application ID** and **Public Key**, and create the
channel with `bot_token`, `channel`, `application_id`, `public_key` and `approver_user_ids`. Set
the **Interactions Endpoint URL** to `https://<your-api>/v1/integrations/discord/interactions`.
Requests are verified with Ed25519 (`X-Signature-Ed25519`) within 5 minutes; *Reject with
reason* opens a Discord form. Needs a public HTTPS URL.

## ntfy

```json
{ "name": "Phone", "type": "ntfy",
  "config": { "topic": "staqly-7f3k9q2", "server_url": "https://ntfy.sh", "access_token": "tk_…", "priority": 4 } }
```

Install the ntfy app and subscribe to the topic. Notifications get **Approve** and **Reject**
actions (they POST the one-tap link) and **Reject with reason** (opens the confirmation page);
tapping the notification opens the item in the dashboard.

<Callout type="warn">
On ntfy.sh **anyone who knows the topic name can read it** — use a long random topic, or a
protected topic with an `access_token` (sent as `Authorization: Bearer`).
</Callout>

## Email (SMTP)

```json
{ "name": "Inbox mail", "type": "email",
  "config": { "host": "smtp.example.com", "port": 587, "username": "apikey", "password": "…",
              "from": "staq.ly <bot@example.com>", "to": ["me@example.com"], "tls": "starttls" } }
```

`tls`: `starttls` (default, port 587, required), `tls` (implicit TLS, port 465) or `none`
(plaintext — only for a trusted local relay; credentials are never sent over plaintext except to
localhost). Multipart text + HTML with Approve / Reject links and a dashboard link; up to 20
recipients.

## Local vs cloud

| | Laptop (local mode) | Cloud / public URL |
|---|---|---|
| Telegram buttons | ✅ polling mode | ✅ polling or webhook |
| Slack / Discord messages | ✅ | ✅ |
| Slack / Discord buttons | ❌ needs a public HTTPS URL | ✅ |
| One-tap links (ntfy, email, …) | only where `NOTIFY_PUBLIC_API_URL` is reachable | ✅ |

**Network policy**: outbound requests are SSRF-guarded — public internet only by default; cloud
metadata and link-local addresses are always blocked. `NOTIFY_ALLOW_PRIVATE=true` allows a LAN
target (self-hosted ntfy, an SMTP relay); `NOTIFY_ALLOW_LOOPBACK=true` a target on the same host.

## Configuration

| Variable | Default | |
|---|---|---|
| `NOTIFY_SECRET_KEY` | — | Key material for encrypting channel secrets (AES-256-GCM). If unset, a random key is generated once into `DATA_DIR/notify_secret.key` (mode 0600). **Back it up with the database** — without it, stored secrets must be re-entered. |
| `NOTIFY_PUBLIC_API_URL` | `PUBLIC_API_URL` | Base URL for decision links and the Telegram webhook |
| `NOTIFY_MAX_FAILS` | `10` | Consecutive failures before a channel is disabled |
| `NOTIFY_MAX_ATTEMPTS` | `5` | Attempts per queued notification |
| `NOTIFY_RETRY_BASE` | `30s` | First retry delay (doubles, capped at 30 min) |
| `NOTIFY_POLL_INTERVAL` | `2s` | Notification outbox worker interval |
| `NOTIFY_LINK_TTL` | `168h` | Decision link lifetime |
| `NOTIFY_ALLOW_PRIVATE` / `NOTIFY_ALLOW_LOOPBACK` | `false` | SSRF policy for channel targets |
| `NOTIFY_TELEGRAM_AUTOREGISTER` | `true` | Call `setWebhook` / `deleteWebhook` when a Telegram channel is saved |
| `TELEGRAM_POLL_INTERVAL` | `3s` | `getUpdates` interval in polling mode |
| `TELEGRAM_API_BASE`, `SLACK_API_BASE`, `DISCORD_API_BASE` | official APIs | Overrides (tests, proxies) |

`compose.yml` passes through `NOTIFY_SECRET_KEY`, `NOTIFY_PUBLIC_API_URL` and
`NOTIFY_ALLOW_PRIVATE`; add others to the `api` service's `environment` if you need them.

## Security

- Channel secrets are encrypted at rest, masked in every response and never logged.
- Every chat button carries an HMAC with a per-channel key, so a modified client can't forge
  decisions for other items or actions.
- Chat decisions apply only to items in the channel's workspace, and only from users on the
  approver allowlist.
- Telegram webhooks are verified with the secret token, Slack with an HMAC signature, Discord
  with Ed25519 (the last two within 5 minutes).
- The confirmation page has no JavaScript and a strict Content-Security-Policy; tokens stay out
  of request logs; per-IP [rate limits](/docs/self-hosting/monitoring#rate-limits) apply.
- Item text is escaped for every target (Telegram HTML, Slack mrkdwn, Discord markdown and
  mentions, email HTML).
