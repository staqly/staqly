title: Custom actions
description: Add buttons such as Regenerate, Publish or Translate to a collection, so reviewers can trigger your automations from an item.

Approve and reject are not always enough. Sometimes a reviewer wants to say "try again,
but make her smile" or "this is good, publish it now". **Custom actions** are extra buttons
you add to a collection for exactly that. You configure them without code. When someone
runs one, staqly records an event and sends it to your [webhooks](/automation/webhooks), and
your automation (n8n, a script, an agent) does the actual work.

For example, n8n receives `item.regenerate_requested` and generates a new image using the
reviewer's feedback.

## What happens when an action runs

1. staqly checks that the item's current status is allowed for this action.
2. It optionally moves the item to a new status (for example `processing`).
3. It stores the feedback (if any) on the item.
4. It records an event and notifies matching [webhooks](/automation/webhooks).

## Adding an action to a collection

Every new collection already has four [default actions](#default-actions). This example adds
a *Translate to German* button next to them.

<Steps>
<Step>

### Define the action

<Tabs items={["Dashboard", "curl"]}>
<Tab value="Dashboard">

Open the collection, click **Settings** and go to **Actions**. Click **Add action** and
fill in the name (required, marked with `*`; `translate`), label, event
(`item.translate_requested`), the status to set (if any), the statuses it is *allowed from*
(`approved`; empty means any status) and whether it needs feedback. Each action's row
summarizes it; if something is wrong, the row shows one validation message in red and
**Save actions** stays disabled until you fix it. **Reset** discards unsaved changes.

</Tab>
<Tab value="curl">

```bash
curl -s -X PATCH http://localhost:3333/v1/collections/$COLLECTION_ID \
  -H 'Content-Type: application/json' -d '{
  "actions": [
    { "name": "regenerate", "label": "Regenerate", "requires_feedback": true, "set_status": "processing",
      "allowed_statuses": ["rejected", "failed"] },
    { "name": "publish", "label": "Publish", "set_status": "processing", "allowed_statuses": ["approved"] },
    { "name": "retry", "label": "Retry", "set_status": "processing", "allowed_statuses": ["failed"] },
    { "name": "archive", "label": "Archive", "event": "item.archived", "set_status": "archived" },
    { "name": "translate", "label": "Translate to German", "event": "item.translate_requested",
      "allowed_statuses": ["approved"] }
  ]
}'
```

`actions` replaces the whole list, so include the ones you want to keep.

</Tab>
</Tabs>

</Step>
<Step>

### Subscribe a webhook to its event

Point a [webhook](/automation/webhooks) at your automation and subscribe it to
`item.translate_requested`, or to `item.*_requested` to receive every action that uses the
default event name.

</Step>
<Step>

### Run it

Approve an item, then click **Translate to German** in the Inbox or on the item page. Your
webhook receives the event with the item, the reviewer's `feedback` and any `payload`.

</Step>
</Steps>

## Default actions

New collections get these four actions unless you pass your own:

| `name` | Label | Allowed from | `set_status` | Event | Feedback |
|---|---|---|---|---|---|
| `regenerate` | Regenerate | rejected, failed | processing | `item.regenerate_requested` | required |
| `publish` | Publish | approved | processing | `item.publish_requested` | optional |
| `retry` | Retry | failed | processing | `item.retry_requested` | optional |
| `archive` | Archive | any | archived | `item.archived` | optional |

## Action definition

| Field | Rules |
|---|---|
| `name` | `^[a-z][a-z0-9_]{0,39}$`, unique; `approve` and `reject` are reserved |
| `label` | Button text; defaults to the name, capitalized, with `_` shown as spaces |
| `event` | Must look like `item.something`; defaults to `item.<name>_requested`. Events staqly emits itself (`item.created`, `item.updated`, `item.deleted`, `item.approved`, `item.rejected`, `item.escalated`, `item.expired`, `item.status_changed`, `item.rule_applied`, `item.completed`, `item.failed`, `item.purged`, `item.tags_changed`, `item.summarized`, `item.unarchived`) are **reserved** (`422`), so receivers can trust them |
| `requires_feedback` | Ask the reviewer for a note (e.g. "make her smile") |
| `set_status` | Optional new status; **never** `approved` or `rejected` (those need the built-in actions and the `items:review` scope) |
| `allowed_statuses` | Statuses the action can run from; empty = any |

A collection can have up to 20 custom actions.

## Running an action

<Tabs items={["Dashboard", "REST", "CLI", "MCP", "TypeScript"]}>
<Tab value="Dashboard">

Custom actions appear next to *Approve* / *Reject* in the Inbox and on the item page,
filtered to the ones allowed in the item's current status. Several selected items can be
processed at once.

</Tab>
<Tab value="REST">

```bash
curl -s -X POST http://localhost:3333/v1/items/$ITEM/actions/regenerate \
  -H 'Content-Type: application/json' \
  -d '{"feedback":"Make her smile","payload":{"variant":"b"}}'
```

`payload` is arbitrary JSON forwarded in the event and webhook. `GET /v1/items/{id}/actions`
lists what the caller may run right now. `POST /v1/items/bulk-actions` runs one action on up
to 100 items (`{"ids":["itm_oalirbz67y4m4cqxq5dw"],"action":"publish"}`), each succeeding or failing independently.

</Tab>
<Tab value="CLI">

```bash
staqly items action itm_oalirbz67y4m4cqxq5dw regenerate --feedback "Make her smile" --payload '{"variant":"b"}'
```

</Tab>
<Tab value="MCP">

`list_available_actions` then `execute_custom_action`:

> *“Regenerate itm_oalirbz67y4m4cqxq5dw with feedback: make her smile.”*

</Tab>
<Tab value="TypeScript">

```ts
await staqly.items.action(itemId, 'regenerate', { feedback: 'Make her smile' })
const actions = await staqly.items.listActions(itemId)
await staqly.items.bulkAction(['itm_1', 'itm_2'], 'publish')
```

</Tab>
</Tabs>

## Permissions and errors

- Running a custom action needs the **`actions:execute`** scope. Sending `edits` with it (to
  change the item while running the action) also needs **`items:write`**.
- An action that isn't allowed in the item's current status returns `409`.
- A missing required feedback returns `422`.
- An action stored before reserved events were enforced that uses one of them refuses to run
  (`409`) until you change its `event`.
