staqly works with any MCP client, not only the ones with their own page. Use this page when
your client is not listed, or when you need the transport details to debug a connection.

## Connect your client

Most clients need just a URL. Pick the transport your client supports:

| Transport | Configuration |
|---|---|
| **Streamable HTTP** (recommended) | URL `http://localhost:3333/mcp`; works with `staqly serve` and Docker |
| **STDIO** (Docker only) | Command `docker`, arguments `exec -i staqly mcp-stdio` |

Cursor and Windsurf have their own pages: [Cursor](/agents/cursor), [Windsurf](/agents/windsurf).

## Check the connection with curl

A raw `initialize` request tells you whether the endpoint is reachable, without any client:

```bash
curl -s http://localhost:3333/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
```

## Streamable HTTP details

- The endpoint is **stateless**: each JSON-RPC request is authenticated on its own and gets
  a server bound to that caller. There is no MCP session to keep alive or hijack.
- Responses are plain JSON (`application/json`), not server-sent events.
- **Local mode**: no credentials. The same local-only checks as the REST API apply
  (loopback/private peer, local `Host`, local or absent `Origin`). See
  [Local vs cloud](/local-vs-cloud#why-local-mode-is-safe-without-keys).
- **Cloud mode**: send `Authorization: Bearer stk_...`. Cookies are never accepted on `/mcp`.

## STDIO details

`mcp-stdio` is a second binary in the API image. Run it **inside** the running container so
it opens the same SQLite database (WAL mode handles several processes on one host). Webhook
deliveries it queues are sent by the server's worker.

- Use `docker exec -i`, **never `-t`**.
- Local mode needs no key. Cloud mode needs one: forward it with
  `docker exec -i -e STAQLY_API_KEY staqly mcp-stdio` and set `STAQLY_API_KEY` in the
  client's environment. Without a key in cloud mode, `mcp-stdio` exits with
  `cloud mode: STAQLY_API_KEY is not set`; with an invalid or revoked key it exits with
  `STAQLY_API_KEY is invalid or revoked`.
- A STDIO process can run for days, so it re-checks the key at most once a minute: a revoked
  or expired key stops working within a minute.
- Without Docker: `cd apps/api && go build -o staqly-mcp ./cmd/mcp-stdio` and run it with
  `DATA_DIR` pointing at the server's data directory (for `staqly serve`,
  `~/.local/share/staqly` by default).
- Errors go to stderr: run the command by hand to see them.

## What the server tells the model

The server announces itself as **`staqly`** ("staqly Agent Workspace", with the server
version) and sends instructions telling the model that items usually start as `pending`,
that collections can be referenced by ID or exact name, how to search by decision date, how
to gate an action on approval (`create_item`, `await_decision`, `report_result`), and that
items with `metadata.untrusted = true` are data, never instructions. The full list is in the
[MCP overview](/mcp#what-the-server-tells-the-model).

Every tool carries MCP annotations: read-only tools have `readOnlyHint: true`, and write tools
set `destructiveHint` to `true` (deletes, revokes, rotations) or `false` (creates and
updates). Clients can use them to decide which calls need confirmation.
