staq.ly speaks two protocols, both backed by the same domain services and the same
authorization checks:

- **MCP** for coding agents — over **Streamable HTTP** at `http://localhost:3333/mcp`
  (recommended) or **STDIO** via `docker exec -i staqly-api mcp-stdio`.
- **REST** for automations and scripts — `http://localhost:3333/v1/...`.

## Which transport?

| | Streamable HTTP | STDIO |
|---|---|---|
| Endpoint | `http://localhost:3333/mcp` | `docker exec -i staqly-api mcp-stdio` |
| Works with a remote / cloud instance | Yes (bearer API key) | No — it opens the database inside the container |
| Sessions | Stateless: every request is authenticated on its own | One process per agent session |
| Recommended | ✔ | When your client only supports STDIO |

<Callout type="warn" title="STDIO: use -i, never -t">
`docker exec -i` keeps stdin open for the protocol. Adding `-t` allocates a TTY and breaks
the JSON-RPC stream.
</Callout>

In **cloud mode**, MCP requires an API key and enforces its scopes: a read-only key cannot
write, `approve_item` / `reject_item` need `items:review`, custom actions need
`actions:execute`. `/mcp` accepts only bearer keys, never browser cookies. See
[MCP tools](/docs/mcp/tools) for the scope of every tool.
